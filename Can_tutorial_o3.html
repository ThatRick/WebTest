Getting Started with Tesla CAN Interfaces

Audience. This tutorial is written for Markus-style automation engineers and programmers who already know the basics of embedded programming and networks, and who prefer the metric system.

⚠️ Legal & safety notice. Everything below is informational. Connecting to, much less transmitting on, a vehicle CAN bus can void warranties, violate local regulations, and – worst-case – interfere with safety-critical systems. Use a listen-only adapter while you learn; keep the wheels chocked and the high-voltage system off when experimenting. You are responsible for any risk you take.

2. What you can read

The good news: Tesla broadcasts a lot of real-time data without authentication. Below are crowd-sourced IDs that have been stable for years on Model S/X and partly on Model 3/Y (double-check on your generation):

CAN ID (hex)Signals (little-endian unless noted)Conversion (metric)
0x118Vehicle speed [15:0]value ÷ 20 → km/h
0x130Steering angle [15:0]value × 0.1 → °
0x237Battery SoC [7:0]value → %
0x12FBrake-pedal percentage [7:0]value → %

Frame list derived from wk057 CAN dump [oai_citation:3‡skie.net](https://skie.net/uploads/TeslaCAN/Tesla%20Model%20S%20CAN%20Deciphering%20-%20v0.1%20-%20by%20wk057.pdf?utm_source=chatgpt.com)

With these four frames you can already build a basic dashboard, datalogger, or automation trigger.

3. What, if anything, you can safely write

  • Body & diagnostic requests. Gateway allows UDS “tester-present” and read DIDs (e.g. VIN) on the diagnostic bus. Useful for querying without risk.
  • Chassis or powertrain commands. Heavily filtered by the Gateway; critical frames often require Tesla’s proprietary RSA signature. Unless you are writing a research tool in a non-moving car, keep transmit OFF.
  • Reverse indicator, horn, etc. Some non-safety functions on Body CAN accept plain frames; use only in a controlled environment.

Rule of thumb: start in listen-only mode (ip link set can0 type can bitrate 500000 listen-only on) [oai_citation:4‡Instructables](https://www.instructables.com/Exploring-the-Tesla-Model-S-CAN-Bus/?utm_source=chatgpt.com), capture the frames you need, and leave TX disabled.

4. Hardware shopping list

  1. Vehicle-side adapter harness
    – Model 3/Y splitter cable (20-pin to RJ-45 + OBD-II) ~ €35 – €50 [oai_citation:5‡EVOffer](https://evoffer.com/product/model-3-y-can-diagnostic-cable/?utm_source=chatgpt.com)
    – Model S/X: 6-pin Autopilot breakout or behind-MCU DB-26.
  2. Micro-controller bridge
    – ESP32-WROOM-32 or ESP32-S3 module.
    – High-speed CAN transceiver (SN65HVD230 or MCP2551) & matching 120 Ω termination.
    – Optional ready-made boards: CANable 2, CANBed M4, CAN-FD Feather.
  3. Dev laptop
    – Any OS; Wi-Fi to ESP32, or USB-Uart-to-CAN dongle (socketcan).
  4. 12 V to 5 V DC-DC for the ESP if you pull power from the vehicle.

5. Suggested ESP32 ⇆ WebSocket ⇆ Phone architecture

Why it works well

  • ESP32 already provides both CAN (via built-in TWAI driver) and Wi-Fi; no Pi needed.
  • Minimal latency – you can push ~800 frames / s on a single WebSocket in binary mode.
  • The phone UI is just an HTTPS page; reload to update, no Play Store deployment.

Pitfalls

  • CAN bus ground offset → use common ground, add TVS protection.
  • Wi-Fi AP in car loses Internet; make the PWA manifest.json display-mode: standalone & offline cache.
  • Hotkeys: instead of transmitting CAN, let them call a cloud webhook (safer) unless the car is parked.

6. Hands-on project – DIY metric speedometer + soft-buttons

  1. Fit the phone behind the wheel. 3-D-print a low-profile cradle (PET-G, heat tolerant) that clips onto the steering-column shroud.
  2. Wire & test CAN.
    1. Ignite-off, connect splitter.
    2. Plug the ESP32-CAN board.
    3. Flash listen-only firmware (sample below).
    4. Check candump logs on the laptop via Wi-Fi.
  3. Filter frames in firmware. Limit to IDs 0x118, 0x130, 0x12F to keep the WS payload tiny.
  4. Serve the PWA. A 20-line index.html drawing a circular dial with SVG, plus a left/right button grid that posts JSON to /hotkey.
  5. Add OTA & TLS. ESP-IDF supports esp_https_server; self-sign a certificate or pin the SHA-256 in the PWA.
Firmware sketch excerpt (Arduino-ESP32 style) 
#include <ESP32CAN.h>
#include <CAN_config.h>
#include <AsyncTCP.h>
#include <ESPAsyncWebServer.h>

CAN_device_t CAN_cfg;
AsyncWebSocket ws("/ws");
AsyncWebServer  server(80);

void setup() {
  Serial.begin(115200);
  // --- CAN init ---
  CAN_cfg.speed = CAN_SPEED_500KBPS;
  CAN_cfg.tx_pin_id = GPIO_NUM_5;
  CAN_cfg.rx_pin_id = GPIO_NUM_4;
  ESP32Can.CANInit();  // listen-only default
  // --- WS ---
  ws.onEvent([](...) { /* ignore */ });
  server.addHandler(&ws);
  server.serveStatic("/", SPIFFS, "/").setDefaultFile("index.html");
  server.begin();
}

void loop() {
  if (auto frame = ESP32Can.CANRead()) {
    if (frame->MsgID == 0x118) {
      uint16_t raw = frame->data.u8[1] << 8 | frame->data.u8[0];
      float kph = raw / 20.0f;
      ws.printfAll("{\"spd\":%.1f}", kph);
    }
  }
}

With an ESP32 bridge and a simple PWA you can build a latency-free, metric speedometer plus soft hotkeys in a weekend, without writing a single line of Android Java. The architecture is solid for read-heavy, write-light applications; just respect the Gateway, stay listen-only until you fully understand every byte you send, and happy hacking!
